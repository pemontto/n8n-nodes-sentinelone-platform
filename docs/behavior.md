# Behaviour contract

## Scope and fields

Alert Get and Update and Alert Note Get Many and Create target IDs and need no scope selection. Alert Get Many and triggers accept optional Account, Site, and Group selections under Options > Scope. Groups require at least one selected Site. Blank IDs are rejected, including values supplied through expressions. Site-scoped credentials can resolve accessible sites even when account-list access is unavailable. An expression that resolves to an empty selection means all records accessible to the credential. A parent alert's current scope must still be validated before an activity is emitted.

When a scope is selected, omitted child selections mean all accessible children beneath it. Child selections are validated by Get Many and triggers, including selections hidden by their parent choice. A Groups selection without Sites is rejected rather than widened. Common alert fields remain present; Additional Alert Fields and Raw Data are opt-in. The common response intentionally exceeds the n8n ten-field simplification recommendation.

## Requests and outcomes

Authenticated n8n request helpers handle network access. Shared read transport retries transient network errors and selected server responses with bounded deadlines and backoff. Mutations are submitted once. Whole-node Retry On Fail is rejected for mutation operations because it can repeat writes. Debug uses redacted request details and cannot affect execution.

Alert Update supports status, analyst verdict, and ticket ID. Rejected updates throw `NodeApiError`; an available HTTP response status is retained, otherwise the service error code is used when present. n8n Continue On Fail and Continue (using error output) handle the thrown error, with the originating item pairing preserved. Error details include `alertId`, `requested`, `errors`, and `mutationAcknowledged: false`. Unknown or partial mutation outcomes are returned as items with `outcome: "unknown"` or `outcome: "partial"` and acknowledgement fields; individual action results include a `status`. Do not retry until the alert has been checked.

Alert Note Create submits once. It compares note snapshots before and after the write to identify a unique matching new note; if the snapshot is incomplete or identification is ambiguous, it returns that status and candidates rather than claiming a particular note was created. An uncertain write must be inspected before another attempt.

## Update verification

Verify Update is enabled by default and reads only changed fields after the mutation. Verification uses a bounded read budget and does not repeat the write. Each output includes `alertId`, `requested`, `outcome`, and `mutationAcknowledged`, with `verification` and `verificationStatus` when verification applies. Scheduled action results remain items; `pending` means SentinelOne acknowledged a scheduled action but readback has not observed the requested values. See [Update verification](ticket-update-verification.md) for status definitions and comparison rules.

## SDL query output

SDL Query Execute accepts a PowerQuery, start/end times, and either Entire Tenant or selected accounts. Output Mode defaults to Rows, emitting one item per row, or Table, emitting one item with `queryId`, `columns`, `values`, and `metadata`. Rows place result columns directly on each item and include `_query` metadata; an empty result still emits one metadata-only item. Metadata reports partial-result reasons, warnings, matching and omitted counts, CPU usage, row counts, and cleanup status.

Options default to a 10 MiB maximum output size, 5,000 maximum rows, 1,500 ms poll interval, and 100 second timeout. Output rows can be truncated to fit byte and row limits, with the partial result described in metadata. An oversized received response fails. SDL cleanup runs after a launched query, including when query execution fails.

## Alert activity delivery

Alert Activity uses SDL V2 LOG queries. Its activity-type selector is a multi-select named Operation that defaults to `["any"]` and accepts the same values as the former Trigger On multi-select, and saved values in the removed Operation field are ignored. Recorded activity conditions inspect one event; Match Conditions is always shown after Recorded Activity Conditions, defaults to Any, and only affects matching when two or more conditions are configured; one condition still applies. Simplify defaults to true and emits a flat event envelope with `changes` only when non-empty and a string `note` only for `noteCreated`; alert summary fields remain present as `null` when unavailable; the full activity shape, including optional `rawActivity` and `currentAlert`, is available with Simplify disabled. Activity IDs are deduplicated within bounded checkpoint and overlap history; later revisions are not monitored. See [the trigger contract](trigger.md) for filters, cursor behaviour, baseline, and delivery limits.

Simplified activity output contains `eventId`, `eventType`, `eventTime`, `activityKind`, `changes` when present, `note` only for `noteCreated`, `actorName`, `alertId`, `alertName`, `alertStatus`, `alertSeverity`, `alertAnalystVerdict`, `accountName`, `siteName`, and `groupName`. Simplified alert output renames `name`, `status`, `severity`, and `externalId` to `alertName`, `alertStatus`, `alertSeverity`, and `alertExternalId`, and omits `eventTimestamp`; other fields and Additional Alert Fields are unchanged. Raw alert output is unchanged.

All trigger modes provide top-level `eventId`, `eventType`, and `eventTime`. Event IDs are slash-separated paths whose components are individually encoded with `encodeURIComponent`: New alerts use host, `alert`, alert ID, and `new`; Updated alerts use host, `alert`, alert ID, `updated`, and exact returned `updatedAt`; activity events use host, `alert`, alert ID, `activity`, and activity ID. Rare duplicates after crashes, state restoration, overlapping executions, and overload are expected; use `eventId` for downstream deduplication and prefer an idempotent destination. The n8n Remove Duplicates node can use Node scope to retain several days of events, and errors when its configured history is full until it is cleared or enlarged.

The activation poll establishes the alert baseline; the first following scheduled poll can emit later matching events. Reads use chronological order and the scheduled poll deadline from `getPollBudgetMs`, with a five-minute fallback. Progress is isolated by stream and scope batch through `resumeMs` and `resumeIds`. Checkpoint state version 2 is re-established from a baseline when absent or unrecognised. Pending activation baselines are retained in memory per workflow, node, and configuration fingerprint until committed state is seen; activation returns no items, so its static data may be discarded. New ID, alert version, and activity ID caches cap at 20,000, 40,000, and 40,000 entries respectively, evict the oldest entry with a warning, and never evict cursor IDs. Alert Activity uses a 300-second overlap. Around 4,000 alerts per minute, New may duplicate around the five-minute overlap.

Only the trigger's own deadline or page cap can return a completed prefix and cursor. API failures, including 429 responses, do not return partial output or advance state. SDL retries 429 according to `Retry-After` only while within its deadline, otherwise it throws with status and retry metadata. Launched SDL queries are cancelled on completion and abandoned work is cancelled before the deadline when possible. A poll that emits and advances nothing fails immediately with its cursor position. Fake-server coverage should verify deadline budgeting and fallback, per-stream/per-scope resume, activation baseline retention, version-2 rebaseline, cache eviction and cursor retention, immediate positioned no-progress errors, no partial state on API/429 failures, SDL Retry-After handling and query cancellation, and deadline/page-cap completed-prefix behaviour.
