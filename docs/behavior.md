# Behaviour contract

## Scope and fields

Alert Get and Update and Alert Note Get Many and Create target IDs and need no scope selection. Alert Get Many accepts optional Account, Site, and Group selections under Options > Scope. Trigger Scope is its own section straight after Credential and Poll Times, containing Accounts, Sites, and Groups saved under `scope.selection`. Sites are hidden until Accounts has a value, and Groups are hidden until Sites has a value. Groups require at least one selected Site. Blank IDs are rejected, including values supplied through expressions. Site-scoped credentials can resolve accessible sites even when account-list access is unavailable. An expression that resolves to an empty selection means all records accessible to the credential. A parent alert's current scope must still be validated before an activity is emitted.

When a scope is selected, omitted child selections mean all accessible children beneath it. Child selections retained in saved parameters are validated by Get Many and triggers. Clearing Accounts in the trigger editor removes hidden Sites and Groups values and includes everything the credential can see. A Groups selection without Sites is rejected rather than widened. Common alert fields remain present; Additional Alert Fields and Raw Data are opt-in. The common response intentionally exceeds the n8n ten-field simplification recommendation.

## Requests and outcomes

Authenticated n8n request helpers handle network access. Reads retry transient network errors and selected server responses with bounded deadlines and backoff. A request timeout caused by the scheduled poll deadline is treated as a deadline stop. If a 429 or 5xx retry cannot fit the remaining deadline after the poll has made progress, the trigger returns the completed prefix, hands the unfinished range to the next poll, and logs the response status; without progress, the HTTP error is returned. Other HTTP errors, including 401, 403, and 404, fail the poll. Mutations are submitted once. Whole-node Retry On Fail is rejected for mutation operations because it can repeat writes. Debug uses redacted request details and cannot affect execution.

Alert Update supports status, analyst verdict, and ticket ID. Rejected updates throw `NodeApiError`; an available HTTP response status is retained, otherwise the service error code is used when present. n8n Continue On Fail and Continue (using error output) handle the thrown error, with the originating item pairing preserved. Error details include `alertId`, `requested`, `errors`, and `mutationAcknowledged: false`. Unknown or partial mutation outcomes are returned as items with `outcome: "unknown"` or `outcome: "partial"` and acknowledgement fields; individual action results include a `status`. Do not retry until the alert has been checked.

Alert Note Create submits once. It compares note snapshots before and after the write to identify a unique matching new note; if the snapshot is incomplete or identification is ambiguous, it returns that status and candidates rather than claiming a particular note was created. An uncertain write must be inspected before another attempt.

## Update verification

Verify Update is enabled by default and reads only changed fields after the mutation. Verification uses a bounded read budget and does not repeat the write. Each output includes `alertId`, `requested`, `outcome`, and `mutationAcknowledged`, with `verification` and `verificationStatus` when verification applies. Scheduled action results remain items; `pending` means SentinelOne acknowledged a scheduled action but readback has not observed the requested values. See [Update verification](ticket-update-verification.md) for status definitions and comparison rules.

## SDL query output

SDL Query Execute accepts a PowerQuery, start/end times, and either Entire Tenant or selected accounts. Output Mode defaults to Rows, emitting one item per row, or Table, emitting one item with `queryId`, `columns`, `values`, and `metadata`. Rows place result columns directly on each item and include `_query` metadata; an empty result still emits one metadata-only item. Metadata reports partial-result reasons, warnings, matching and omitted counts, CPU usage, row counts, and cleanup status.

Options default to a 10 MiB maximum output size, 5,000 maximum rows, 1,500 ms poll interval, and 100 second timeout. Output rows can be truncated to fit byte and row limits, with the partial result described in metadata. An oversized received response fails. SDL retries query-polling 404 responses for a bounded indexing period and retries 429 responses according to `Retry-After` only while within its deadline. SDL query cleanup is best effort; cleanup failures are logged as warnings and do not replace the query result or its original error.

## Alert activity delivery

Alert Activity uses SDL V2 LOG queries. Its activity-type selector is a multi-select named Operation that defaults to `["any"]` and retains the former Trigger On values and adds Agentic Investigation Triggered (`16008`) and Other (Unrecognised Types) (`unknown`); saved values in the removed Operation field are ignored. The former custom activity type ID option has been removed, so saved values for it are ignored. Other selects alert-linked types outside `16000` to `16005`, `16007` and `16008`, including undescribed type `16006`; it combines with selected IDs using OR. Any applies no type filter. Agentic investigation events have `activityKind: "agenticInvestigationTriggered"` and no expected change data. Activity conditions inspect one event; Match Conditions is shown after Activity Conditions, defaults to Any, and only affects matching when two or more conditions are configured; one condition still applies. Simplify defaults to true. Activity changes use a concise `change` object for status, analyst verdict, severity, and assignee events, and `changes` for other events with supplied changes; either is omitted when there is no change. Simplified output can also include mitigation details and the optional `rawActivity` and `currentAlert` records when their options are enabled. Activity IDs are deduplicated within bounded checkpoint and overlap history; later revisions are not monitored. See [the trigger contract](trigger.md) for filters, cursor behaviour, baseline, and delivery limits.

Simplified activity output contains `eventId`, `eventType`, `eventTime`, `activityKind`, `actor` (`id`, `name`), `alertId`, `alertName`, `alertStatus`, `alertSeverity`, `alertAnalystVerdict`, `alertExternalId`, `accountId`, `accountName`, `siteId`, `siteName`, `groupId`, and `groupName`, `activityTypeId` for unknown types, plus `change` or `changes`, `note`, `mitigation`, `rawActivity`, or `currentAlert` when applicable and enabled. Simplified alert output renames `name`, `status`, `severity`, and `externalId` to `alertName`, `alertStatus`, `alertSeverity`, and `alertExternalId`; it flattens scope into `accountId`, `accountName`, `siteId`, `siteName`, `groupId`, and `groupName` and omits `scope` and `eventTimestamp`. Additional Alert Fields are prefixed with `alert` (for example, `alertAnalystVerdict`). Raw alert output is unchanged.

All trigger modes provide top-level `eventId`, `eventType`, and `eventTime`. Event IDs are slash-separated paths whose components are individually encoded with `encodeURIComponent`: New alerts use host, `alert`, alert ID, and `new`; Updated alerts use host, `alert`, alert ID, `updated`, and exact returned `updatedAt`; activity events use host, `alert`, alert ID, `activity`, and activity ID. Rare duplicates after crashes, state restoration, overlapping executions, and overload are expected; use `eventId` for downstream deduplication and prefer an idempotent destination. The n8n Remove Duplicates node can use Node scope to retain several days of events, and errors when its configured history is full until it is cleared or enlarged.

The activation poll establishes the alert baseline; the first following scheduled poll can emit later matching events. Updated events can arrive before New events because the two streams progress independently. Reads use chronological order and the scheduled poll deadline from `getPollBudgetMs`, with a five-minute fallback. Progress is isolated by stream and scope batch through `resumeMs` and `resumeIds`; an interrupted New read resumes with its overlap so late arrivals can still be found. Checkpoint state version 2 is re-established from a baseline when absent or unrecognised. Because n8n 2.38.1 can discard static data when a poll returns no items, a pending baseline is retained in memory by workflow and node, with its configuration fingerprint. A configuration change resets it, including a change from A to B and back to A; it expires after one hour, and only empty scheduled polls refresh it. New ID, alert version, and activity ID caches cap at 20,000, 40,000, and 40,000 entries respectively, evict the oldest entry with a warning, and never evict cursor IDs. Alert Activity uses a 300-second overlap. Around 4,000 alerts per minute, New may duplicate around the five-minute overlap.

Only a deadline or page cap can return a completed prefix and cursor. Permanent API failures do not return partial output or advance state. A retryable 429 or 5xx response that cannot be retried within the remaining deadline returns the completed prefix only if polling has already made progress; otherwise the HTTP error is returned. SDL retries 429 according to `Retry-After` within its deadline and allows a bounded 404 indexing delay while polling a launched query. Launched SDL queries are cancelled on completion and abandoned work is cancelled before the deadline when possible; cleanup failures produce warnings. Manual alert previews search newest windows first; if a dense window exceeds the configured page cap, the preview reports the limit instead of splitting the window to try to fill the result. A poll that emits and advances nothing fails immediately with its cursor position. Fake-server coverage should verify deadline budgeting and fallback, per-stream/per-scope resume, activation baseline retention, version-2 rebaseline, cache eviction and cursor retention, immediate positioned no-progress errors, no partial state on permanent API failures, retryable response handoff after progress, SDL Retry-After and indexing-delay handling and query cancellation, and deadline/page-cap completed-prefix behaviour.
