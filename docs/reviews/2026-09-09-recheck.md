## New correctness findings

**A deleted or invisible alert wedges the trigger permanently.** Every activity's alert must resolve. `ActivityNotePoll.ts` throws "could not resolve current alert scope for an activity; retry after alert indexing completes" whenever `lookup.unresolvedIds.size` is non-zero, and nothing is saved, so the checkpoint never advances. An alert purged by retention, or one the credential cannot read via unified alerts while it can read the activity feed, never resolves. The workflow stops delivering events until someone resets state or changes an option, which re-baselines and discards the backlog. Fix: keep the hard failure only while the activity is younger than the overlap; once older, record it as seen, drop it, and log a warning naming the alert ID. Not covered by tests.

**A polling outage becomes unrecoverable.** The checkpoint holds on failure while the window end is the poll start, so the queried range grows without bound. `readActivityFeed` bisects on the 1,000-row cap under a fixed budget (128 queries, 300 s), so a busy tenant after hours of downtime throws "exceeded the query budget or deadline" on every poll, which pins the checkpoint again. Fix: advance the checkpoint in bounded slices, emitting per slice, so a poll always makes progress.

**`fullOutput` in `readActivityFeed` is inert.** Validated at `ActivityFeed.ts:279`, never read again; `decodeLog` always attaches `rawActivity`. Correct today only because `output()` copies it conditionally. Fix: strip `rawActivity` in `decodeLog` when `fullOutput` is false.

**Duplicated seen-state doubles static data.** `ActivityNotePoll.ts:395-396` writes both `seenActivityIds` and `seenActivityTimestamps`; nothing reads `seenActivityIds`. At the 40,000 cap that is a redundant multi-megabyte array rewritten each poll. Fix: drop it.

**`pages()` discards HTTP error metadata.** It catches the `NodeOperationError` from `authenticatedRequest` and rethrows a bare `Error`, which the poll handler prefixes again. Same class as the existing double-wrapping finding.

Checked clean: activity type IDs are digit-validated before SDL filter interpolation; alert IDs and account scope are re-verified against the request; cursor repetition and page limits terminate pagination; enum values in `ActivityConditions.ts` match the observed source strings; manual preview never writes state.

## Trigger editor UI

**Group scope silently stops filtering when Sites is cleared.** `nodes/shared/Descriptions.ts:107-110` gates Group Names or IDs on `siteIds` existing, but `[]` passes the `exists` condition, so the field is always visible. `SentinelOnePlatformTrigger.node.ts:660` reads `groupIds` only when `siteIds.length > 0`. Pick sites and groups, clear Sites, and the still-populated Group field is ignored: the trigger polls the whole account while the editor shows two groups. Fix: throw in `poll()` when `groupIds` is set with no `siteIds`.

**Clearing Activity Types produces an error about the condition builder.** `activityTypes` (`:52-72`) is optional; an empty selection hits `invalid()` in `ActivityConditions.ts:66-73`, whose message points at the condition builder. Fix: `required: true` and a message naming Activity Types.

**Mitigation dropdowns show raw API enums** (`BLOCKLIST_ADD`, `PENDING_REBOOT`) at `:167-185`, built as `name: value` in `ActivityConditions.ts:29-35`. Fix: Title Case names, keep values as the allow-list.

**Two Options collections duplicate seven field definitions verbatim** (`:410-444` and `:487-563`). `severities` and `statuses` reuse the same parameter names under different meanings, so a severity chosen for Alert reappears as Current Parent Alert Severity after a resource switch. Fix: shared builders in `Descriptions.ts`; rename the activity variants to `parentSeverities` and `parentStatuses`.

**The Any sentinel can be combined with real types** (`activityTypes`, `:52`); the selection then lies. Fix: drop the sentinel and treat empty as all, or surface it as a hint.

**Codex metadata.** Both `.node.json` files omit `alias` (no hits for "S1", "EDR", "XDR"). `"categories": ["Security"]` is not a rendered n8n category. Use a standard category and keep Security as an alias.

Smaller: subtitles disagree ("Get: Alert" vs "Alert: New"); Match Conditions lists Any before All; several descriptions exceed 100 characters (`:94-95`, `:501-502`, `:518-519`); comma-separated assignment fields (`:141-166`) lack placeholders.

## n8n re-triage

A further pass re-read every finding above against the n8n guide and the n8n core in this package's tree (n8n-workflow 2.37.4, @n8n/backend-network 1.11.4). Most smell, test, and docs items are confirmed as written but are not verification blockers and do not change runtime behaviour. Treat them as backlog.

Dropped or downgraded: `group: ['output']` (both values are valid); `Object.create(null)` on item json (re-serialised on persist); `activePollKeys` Set (polling triggers run only on the main instance, key is workflow plus node); long functions and parameter counts (maintainability only); 100-character descriptions and the Return All cap as such (style guidance, not rules; the hidden throw is the defect).

Upgraded by n8n behaviour:

- Rejected update as success: the item carries no `error` key, so Error output, continueOnFail, Retry On Fail, and tool mode all see success.
- `usableAsTool`: in tool mode the model fills Alert ID and ticket values via `$fromAI`, so alert text reaches parameters, not just prose. Restrict to read operations.
- Trigger wedges: n8n records a failed execution every interval and can auto-deactivate the workflow. `pollTimes` is injected by n8n, so the user cannot widen the interval to recover.
- Seen-state duplication: static data is written to the workflow row after every production poll, so the redundant array is a multi-megabyte DB write per interval.

New n8n-specific bugs:

1. Retry-After is never honoured. `retry.ts:33-49` reads headers on the error, but `httpRequestWithAuthentication` returns a `NodeApiError` with the axios error on `cause`, so every 429 waits the fixed 1 s/2 s ladder. The network-code branch at `retry.ts:22-27` is dead for the same reason. Fix: unwrap `cause` before reading, and test with real `NodeApiError` shapes.
2. Credential test hits `/web/api/v2.1/sites`, which proves nothing about unified-alerts GraphQL or SDL scope. Green tick, then 403 at runtime.
3. Blank console URL throws a raw expression error from the `baseURL` template instead of a field error.
4. `require-node-api-error` lint only fires inside catch blocks, so a passing lint is not evidence the bare SDL `Error` is compliant.

## What actually matters

Six things change what a user sees. Everything else is backlog.

1. Token follows cross-origin redirects in the trigger.
2. Rejected update reported as success on every n8n failure surface.
3. Trigger wedges permanently on an unresolvable alert or after a long outage.

6. Credential test passes for a token the node cannot use.
